Part 1
문제 좁히기 사례
수강생이 작성한 넓은 과제를 보고, 오늘 만들 수 있는 한 단계로 줄이는 법

오늘 하는 것과 하지 않는 것

오늘 하는 것
  • 내 업무 중 작은 한 단계 고르기
  • 그 단계에 필요한 데이터 정리하기
  • AI에게 알려줄 기준 문서 만들기
  • 단일 에이전트 한 번 작동시켜보기
  • 반복할 수 있는 작업인지 판단하기
오늘 하지 않는 것
  • 전체 업무 자동화
  • 멀티 에이전트 구성
  • 웹 서비스 / DB / API / MCP 구축
  • 완성도 높은 시스템 제작
  • 지난주 과제 완성
오늘 목표는 완벽한 시스템이 아닙니다. AI에게 맡길 첫 번째 업무를 하나 골라서 한 번 돌려보는 것 — 그거면 됩니다.

왜 문제를 좁혀야 하는가

비유로 이해하기
에이전트 만들기는 큰 부서 하나를 세우는 일이 아닙니다.
신입 한 명에게 첫 업무 지시서를 쓰는 것에 가깝습니다.

"정산 업무 전체 다 해줘"라고 하면 어렵습니다.
대신 "이 엑셀에서 이상한 금액만 찾아서 표시해줘"라고 하면 훨씬 잘 작동합니다.

오늘은 AI에게 맡길 첫 번째 업무 지시서를 만드는 날입니다.
처음부터 크게 하면 어려운 이유설명
필요한 데이터가 많아짐업무 전체를 다루려면 자료 준비만도 한참 걸림
판단 기준이 복잡해짐단계마다 다른 기준이 필요해서 AI에게 설명하기 어려워짐
성공 기준이 흐려짐무엇이 잘 된 건지 판단하기 어려워짐
오늘 결과를 못 봄실습 시간 안에 작동 여부를 확인하기 힘듦

"좁힌다"는 게 구체적으로 어떤 뜻인가

"문제를 좁혀라"고 하면 막연합니다. 좁힌다는 게 뭔지 한 줄로 줄여보면 이렇습니다.

Before / After 사례

사례 1. 재무·정산 업무

Before — 너무 넓다
재무 업무 전체를 자동화하고 싶다
  • 데이터 확인
  • 금액 검증
  • 이상값 탐지
  • 보고서 작성
  • 승인 요청
After — 좁혔다
엑셀에서 이상값을 찾아 요약 메모를 만드는 에이전트
  • 입력: 엑셀 파일 (CSV 변환)
  • 출력: 이상값 목록 + 한 줄 요약
  • 매주 반복 → 반복성 충족
  • 기준 명확 → 명확성 충족

사례 2. 연구·정책 리서치

Before — 너무 넓다
정책 동향 리서치 보고서를 자동화하고 싶다
  • 검색
  • 자료 선별
  • 요약
  • 비교
  • 시사점 작성
After — 좁혔다
뉴스 기사 5건을 같은 기준으로 요약하고 공통 키워드를 뽑는 에이전트
  • 입력: 기사 본문 텍스트
  • 출력: 기사별 핵심 요약 + 공통 키워드
  • 보고서 쓸 때마다 반복
  • 형식 고정 가능

사례 3. 행사·교육 운영

Before — 너무 넓다
교육 운영 전체를 자동화하고 싶다
  • 신청자 확인
  • 안내 메일 작성
  • 참석자 명단 정리
  • 만족도 조사 정리
  • 결과 보고서 작성
After — 좁혔다
참석자 명단 CSV를 기준으로 안내 메일 초안을 만드는 에이전트
  • 입력: 참석자 명단 CSV + 교육 일정
  • 출력: 안내 메일 초안 + 누락 정보 체크리스트
  • 행사마다 반복
  • 메일 형식 고정 가능

사례 4. 보고서 작성

Before — 너무 넓다
기술동향 보고서 전체를 자동화하고 싶다
  • 자료 수집
  • 분석 및 정리
  • 초안 작성
  • 검토 및 수정
  • 최종 편집
After — 좁혔다
논문·뉴스 3건을 요약해서 보고서 서두 단락으로 만드는 에이전트
  • 입력: PDF 또는 기사 본문 텍스트
  • 출력: 핵심 내용 3줄 + 시사점 1줄
  • 보고서 쓸 때마다 반복
  • 출력 형식 고정

발표 멘트

처음부터 큰 업무 전체를 자동화하려고 하면 생각보다 어렵습니다. 업무 단계가 많아지고, 필요한 데이터도 많아지고, 판단 기준도 복잡해지기 때문입니다.

그래서 오늘은 전체 업무를 완성하는 게 아니라, 그 안에서 가장 먼저 작동시켜볼 수 있는 한 단계를 고르는 것이 목표입니다.

문제를 좁힐 때는 세 가지를 보면 좋습니다. 잠깐 pause 자주 반복되는 일인지, 입력과 출력이 분명한지, 오늘 안에 결과를 확인할 수 있는지입니다.

예를 들어 정산 업무 전체를 자동화한다고 하면 범위가 너무 큽니다. 하지만 그중에서 엑셀의 이상값을 찾아 요약하는 일로 줄이면 훨씬 명확해집니다.

오늘은 AI에게 맡길 첫 번째 업무를 정하는 것만으로도 충분합니다.

데이터 확보로 이어지는 부분
문제를 좁힌 뒤에는 해당 과업에 필요한 데이터가 무엇인지 정리해야 합니다. 데이터 확보·구조화는 별도 담당 파트에서 이어서 다룹니다.

암묵지란 무엇인가

쉽게 말하면
암묵지는 "내가 당연하게 하고 있던 일 처리 기준"입니다.

나는 당연히 아는 기준이라 말하지 않았지만, AI는 그 기준을 모릅니다.
그래서 AI가 이상한 결과를 낼 때는 "AI가 못한다"가 아니라 "내 기준을 아직 안 알려줬다"라고 보는 게 좋습니다.

회의 원문

A: 이번 주 목요일 교육은 멀티 에이전트까지 가기 어렵습니다. B: 맞습니다. 수강생들이 VS Code도 아직 익숙하지 않아서 단일 에이전트부터 가는 게 좋겠습니다. C: 그러면 오전에는 문제 좁히기와 데이터 확보, 오후에는 기준 문서와 스킬을 다루면 어떨까요? A: 좋습니다. 그 방향으로 정리하겠습니다. B: 데이터 보안 안내도 꼭 넣어야 합니다.
기준 없이 요약하면
  • 목요일 교육이 어렵다는 이야기가 나왔다
  • VS Code가 어렵다는 이야기도 있었다
  • 오전과 오후를 나눠서 진행하기로 했다
  • 데이터 보안도 중요하다고 했다

기준 문서(MD 파일) 만들기

기준 문서는 에이전트에게 업무 기준을 알려주는 파일입니다. VS Code에서 기준문서.md를 만들고 아래 구조로 채우면 됩니다.

기준 문서 예시 1 — 회의록 작성

# 회의록 작성 기준 ## 1. 목적 회의 내용을 핵심 중심으로 정리한다. ## 2. 출력 형식 - 회의 개요 (일시, 참석자, 주제) - 결정 사항 - 액션 아이템 (담당자 + 기한) - 보류 사항 ## 3. 판단 기준 - 결정된 내용과 논의 중인 내용을 반드시 구분한다. - 담당자와 기한이 없는 할 일은 액션 아이템이 아니라 보류로 분류한다. - 보고용은 격식체, 팀 공유용은 평서체로 쓴다. ## 4. 하면 안 되는 것 - 확인되지 않은 내용을 결정사항처럼 쓰지 않는다. - 발언자를 지나치게 상세히 나열하지 않는다.

기준 문서 예시 2 — 뉴스 요약

# 뉴스 요약 기준 ## 1. 목적 뉴스 기사를 업무 참고용으로 빠르게 파악한다. ## 2. 출력 형식 - 기사 핵심 요약 3줄 - 관련 기관/기업 - 업무상 참고할 점 - 추가 확인 필요 사항 ## 3. 판단 기준 - 단순 사건 설명보다 업무에 영향을 줄 수 있는 내용 우선 정리 - 추측성 표현은 제외 - 출처 불명확한 내용은 "추가 확인 필요"로 표시 ## 4. 하면 안 되는 것 - 기사에 없는 내용을 임의로 해석하지 않는다. - 확인되지 않은 전망을 사실처럼 쓰지 않는다.

기준 문서 예시 3 — 엑셀 이상값 점검

# 엑셀 이상값 점검 기준 ## 1. 목적 엑셀 데이터에서 확인이 필요한 값을 찾아낸다. ## 2. 출력 형식 - 이상값 목록 - 이상값으로 판단한 이유 - 담당자가 확인해야 할 질문 ## 3. 판단 기준 - 빈 값이 있는 행은 확인 필요로 표시 - 전월 대비 차이가 큰 값은 확인 필요로 표시 - 단, 사유 컬럼에 예외 사유가 있으면 예외로 분류 ## 4. 하면 안 되는 것 - 이상값을 오류로 단정하지 않는다. - 원인을 추측해서 쓰지 않는다.
한 줄로
AI가 못하는 게 아니라,
내가 일하는 기준을 아직 알려주지 않은 것일 수 있습니다.
발표 멘트

회의록은 단순히 회의 내용을 줄이는 문서가 아닙니다. 좋은 회의록은 결정된 내용, 논의 중인 내용, 담당자가 해야 할 일을 구분하는 문서입니다.

그런데 그 구분 기준은 사실 평소에 회의록을 쓰는 사람의 머릿속에만 있습니다. 잠깐 pause 그래서 AI에게 회의록을 시키면 단순 요약이 나오는 거죠.

같은 회의 내용이라도 "결정사항과 논의 중인 것을 구분해라, 담당자와 기한이 있으면 액션 아이템으로 분리해라"라는 기준을 한 번만 알려주면, 그때부터 결과물이 완전히 달라집니다.

즉, AI가 못한다고 느껴질 때 가장 먼저 의심해야 할 것은 "내가 평소 쓰던 기준을 아직 안 알려줬구나"입니다.

스킬이란
스킬은 매번 새로 설명하지 않아도 되게 만드는 반복 실행 버튼입니다.

한 번 기준을 잘 만들어두면, 다음부터 같은 일을 할 때 그 기준을 다시 설명하지 않아도 됩니다.

모든 업무를 스킬로 만들 필요는 없어요. 아래 질문으로 판단하세요.

발표 멘트

스킬은 어렵게 생각하지 않으셔도 됩니다. 매번 같은 기준을 다시 설명하지 않아도 되게 만드는 반복 실행 버튼이라고 보면 됩니다.

예를 들어 회의록을 매번 같은 형식으로 정리해야 한다면, 그 기준을 매번 프롬프트로 다시 쓰는 건 번거롭습니다. 잠깐 pause 이럴 때 회의록 작성 기준을 스킬로 만들어두면, 회의 내용만 넣어도 같은 구조로 결과물을 받을 수 있습니다.

다만 모든 작업을 스킬로 만들 필요는 없습니다. 자주 반복되고, 출력 형식이 정해져 있고, 매번 같은 기준으로 처리해야 하는 업무부터 스킬로 만드는 게 좋습니다.
